While I was away in Düsseldorf, and when I got back, I received a notification in [Artemis](http://artemis.jamesg.blog/) asking whether I wanted to change the time zone in which the reader was set. It is important that the user’s timezone is correct so that Artemis can continue to update at midnight in the user’s time zone. Here is what the notification looked like when I got back, in which I am prompted to change my time zone from Europe/Berlin to Europe/London:

![A yellow banner at the top of the Artemis interface, above the navigation bar, that informs the user their current time zone is different to the one set for their account.](https://editor.jamesg.blog/content/images/2026/05/timezones.png)

ALT

A yellow banner at the top of the Artemis interface, above the navigation bar, that informs the user their current time zone is different to the one set for their account.

This feature works by checking the user’s time zone with JavaScript. If the user is in a different time zone to the one in which their account is configured, the notification will appear. The notification can be dismissed, which sets a value in `localStorage` that remembers the user no longer wants to see the notification. <sup class="footnote-reference" id="f-1"><a href="https://jamesg.blog/longform-feed#1">1</a></sup>

This has me thinking about what it means to design software with travel in mind.

Artemis has a few features related to travel. First, because Artemis is designed with mobile use in mind, the software can be used on the go. Second, Artemis lets you disable your reader at any time using the [holiday and break mode](https://jamesg.blog/2025/07/02/designing-calm-software-with-breaks-in-mind) feature. Third, as aforementioned, Artemis notifies you when you may have changed time zones so you can update your settings as required.

I also experimented with a “catch-up” mode that lets you see posts grouped by author when you return from a break. The idea was it may be easier to look at posts grouped by author instead of chronologically after you have been away for a few days. Chronological presentation allows you to retain the context of what individual authors have been writing about over time. This feature is currently not working and may need revision, but I certainly want to come back to this idea at some point.

How software is designed with travel in mind depends on the nature of the software. For example, on my recent trip I had to install an application to book a ticket for a train. I noticed the application was \~50 MB so it could install quickly, which was important because I was doing this underground (where mobile signal may be weaker), while waiting for the train (which meant I needed to work fast).

The small size let me download the application fast, and was especially meaningful in a context where I had limited time before the train I wanted to catch arrived. I am unsure if the software was explicitly designed to be as small as possible, but the small app size relative to others caught my eye and felt like the minimal software size could be an intentional design goal. <sup class="footnote-reference" id="f-2"><a href="https://jamesg.blog/longform-feed#2">2</a></sup> <sup class="footnote-reference" id="f-3"><a href="https://jamesg.blog/longform-feed#3">3</a></sup>

Are there any other examples of software design where specific affordances are made for someone while traveling? I suspect there are so many! If any come to mind, feel free to send me an email at readers@jamesg.blog.
