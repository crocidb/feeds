[Artemis](https://artemis.jamesg.blog/), the calm web reader I maintain, supports web feeds marked up with [h-feed](https://indieweb.org/h-feed). h-feed allows you to create a web feed in HTML using microformats. A h-feed may contain zero or more h-entries, each h-entry representing an entry in the feed. For example, my [longform feed](https://jamesg.blog/longform-feed) page is a h-entry. I use Granary to convert the longform feed page into RSS.

While h-feed is commonly used for marking up lists of blog posts, it can be used for anything. For example, [Tantek has a “daylists” page](https://tantek.com/daylists) on his website that lists daylists generated by Spotify based on his music tastes. This feed contains a h-entry for each daylist.

Uniquely, each entry in the daylists feed does not have a unique URL. Herein lies a story that I want to document both for any interested reader and web reader developers.

Identifying a problem
----------

At [IndieWebCamp Nürnberg](https://indieweb.org/2026/Nuremberg) last weekend, I realised that Tantek’s daylists were not showing up in Artemis. This was because Artemis has a unique constraint in the database that says if a given URL and user ID combination already exists in the `posts` table, a record with matching values should not be inserted again.

Artemis falls back to the feed URL (`https://tantek.com/daylists`) in lieu of having a specific URL for each entry. This logic meant that new entries to the feed were not being added as expected, because two records couldn’t have the same URL and user ID combination.

My solution
----------

During the IndieWebCamp, I came up with a solution to this problem: if an entry in a feed does not have a URL already, Artemis should compute one based on the content of the entry.

Now, when a post is retrieved in a feed, Artemis computes a SHA 1 hash using the content in a post to which the URL of the post is appended. A hex digest is then calculated from the hash. Here is what the full calculation looks like:

```
hashlib.sha1((item["object"]["content"] + item["url"]).encode("utf-8")).hexdigest()

```

This digest is then saved in the record for a post, and appended as a fragment onto the end of a URL. A flag is then saved in a record that says that a custom URL has been computed because a unique one was not found for an entry.

Here is an example of such a custom URL:

```
https://example.com/#854cfaf127ca2f2d11a53d879d96a064e33facaf
```

This hash is appended to the URL because of constraints associated with the database Artemis uses, SQLite. Ideally, the hash would be stored separately and the URL could be the same. But, I cannot use an `ALTER TABLE` command to add a new column. The SQLite documentation for the `ALTER TABLE` command documents the following limitation: “[The column [that you are creating] may not have a PRIMARY KEY or UNIQUE constraint.](https://www.sqlite.org/lang_altertable.html)”

Thus, the hash is appended to a URL. This allows Artemis to save a record because each URL will now be unique because its hash is based on the content in a post and the URL of the feed.

Once I added this logic, all of Tantek’s daylists posts started to show in Artemis. In addition, a (work-in-progress) project I made a while ago that scrapes Wikipedia and creates a h-feed of discography for an artist started to work again. For example, records on `https://jamesg.blog/music-api?url=Lorde` did not have unique URLs, and so Artemis didn’t add all the records. But now Artemis computes a custom URL for each entry based on its content, so Artemis can store all the posts it has found from the feed.

When the user’s feed is computed, the hash is removed. This means that a user doesn’t know that a custom URL has been computed for an entry: indeed, all of the above logic pertains entirely to technical details.

Ideally, any feed where a record is published on a page would have at minimum a fragment link to that section of the page. With that said, part of my job as a web reader maintainer is to make the experience for users as good as possible even when feeds may not contain complete markup. I think the solution I have come up with works well in this regard: users see all the content published by a feed (which is absolutely essential), without knowing any of the behind-the-scenes going on to ensure the post shows up.

Lessons learned
----------

I learned a few lessons from working on this project. First, posts, especially h-entry records inside a h-feed, may not contain a URL. This means that relying explicitly on a URL as part of a unique constraint in a database may not be prudent. Second, that I can’t add a column with a `UNIQUE` constraint in SQLite after a table has been created.

Third, this bug meant that I missed posts in my feed. This is an important lesson because the more I maintain Artemis the more I realise how important it is for me to be able to verify that the polling system is working as expected. This is something I am actively thinking about, for which a large part of the solution would be tests and a more rigorous monitoring system.

All in all, this was a fun project to work on. When I worked on my solution, I knew I should write it down. After supporting h-feed markup for more than a year I had not yet knowingly run into a case where a feed had entries without URLs. I wanted to create a written artefact of this edge case and my solution so that anyone working with h-feed markup that contains h-entry records without URLs, or any feed format where a URL may not be assigned for each entry, can reason with the potential implications and ensure all posts continue to show up as expected in a reader.

Now, Artemis can handle feeds whose entries do not have URLs, creating unique URLs behind the scenes so that all posts can be saved and displayed in a user’s feed without exposing the seams of my implementation.
