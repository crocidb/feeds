By default, the [Artemis reader interface](https://artemis.jamesg.blog) does not show a link to hide a post or unsubscribe from an author. This is available on desktop devices if you press the “h” key on the keyboard (something that I need to change because “h” I have a concern that the single key may coincide with a screen reader shortcut <sup class="footnote-reference" id="f-1"><a href="https://jamesg.blog/longform-feed#1">1</a></sup>), or if you toggle a setting to permanently show said links in the interface.

The interaction
----------

For a while, I have wanted a swipe-based interaction suitable for mobile devices. This would let you swipe a post in the reader to see a menu of actions, such as a button to hide a post. I tried implementing this in JavaScript earlier this year. The code was relatively messy and the UI was glitchy. I didn’t release the feature. This week, I took a new approach: I used the native [CSS scroll snap API](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll_snap) to create a swiping menu.

Here is how the menu looks:

In the video above, there is a list of posts in the Artemis reader. Each list entry shows a post title and its corresponding author. When I swipe right, two buttons appear: one to hide the post, and another to unsubscribe from the author who published the post. When I swipe left again, the post title and author show again.

You can see my cursor in the video because I am emulating the effect in the Firefox mobile emulator, and using my cursor for the touch action. But you can imagine the cursor being my thumb holding onto an item to move it. *(Note: on desktop devices outside of the Firefox mobile emulator, using the cursor doesn’t move the box, but moving the trackpad does.)*

This is implemented with *no JavaScript*. CSS handles the scrolling and, as a result, it works smoothly.

Implementation
----------

I modelled the implementation in a static HTML file, which I then expanded into three different swipe variants:

1. Swipe right to show an icon that appears next to the main item.
2. Swipe right to show a panel that occupies the whole element space (this is the variant in the GIF above).
3. Swipe left to show an icon, and swipe right to show another.

[You can try out all of these variants in my playground.](https://playground.jamesg.blog/scrollsnap-experiment.html) You can also inspect all of the variants in my playground to see how they work.

The third variant is not ideal: it requires JavaScript to automatically scroll to the middle panel. Using JavaScript was the only way that I could think of to make sure the middle panel was centred on page load. It is also a bit unintuitive from a UX perspective in that, when you show either the left or right menu, swiping in the opposite direction can take you to the far-opposite end, as opposed to the next item in the list. Nevertheless, the first two variants are interesting to me.

I implemented the feature using custom HTML elements. There are two elements: `scroll-panel`, which can contain one or more `panel-item` elements. You can use the “left” and “right” classes to specify if a panel is to be seen only when swiping left or right (the code could be better architected, but my main focus was on getting the functionality right; *first make it work, then make it elegant*). I don’t use the custom components API, meaning you don’t need JavaScript to register the component. Instead, you can copy the HTML code and the CSS and the panels should work (as long as your browser supports scroll snap).

I am using flex box to control the size of the elements inside each scroll panel. I am not exactly sure how the flex box works, having relied on Stack Overflow threads to help me implement it. But I think this speaks more to my limited understanding of flex box generally, an area about which I should learn more.

Limitations
----------

One limit to my implementation is, as yet, there is no [progressive enhancement](https://indieweb.org/progressive_enhancement): I haven’t tested this code in a browser that doesn’t support scroll snap, so it’s likely the panel will appear unexpectedly in those environments. I should design a fallback experience that hides the button panels entirely if this API is not supported.

Secondly, in the case of the Artemis implementation, there is no affordance that visually indicates that the swipe action does anything. This is something I will need to work on. Perhaps a visual cue could appear for users that they can dismiss? Such cue would only appear once per account registration. This came up when I brought the idea to [Front End Study Hall](https://indieweb.org/events/2026-11-12-front-end-study-hall). Related to the swiping action, the question for me is: *Since I have made an experience that is not immediately visible to users, how can I ensure users can find it?*

⁂ ⁂ ⁂

The most delightful thing about designing this component is that CSS is doing all the work. As aforementioned, my JavaScript implementation had several flaws. Whereas the CSS scroll snap feature works out of the box. It is a delight to be able to implement a feature that feels so natural on mobile devices – swiping to take an action on item in a list – without having to rely on JavaScript.
